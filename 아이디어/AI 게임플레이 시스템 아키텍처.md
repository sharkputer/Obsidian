# AI 게임플레이 시스템 아키텍처 — "프로게이머-코치" 모델
[[AI 게임플레이 유튜브 기획]]에서 정한 방향을 실제 시스템으로 옮기기 위한 공통 아키텍처. 고군분투로 처음 구현하지만, 설계 원칙은 "게임이 바뀌어도 갈아끼우는 부분만 바꾸면 되도록" 잡았다.

## 설계 목표
1. 게임이 바뀔 때 새로 만들어야 하는 부분과, 계속 재사용되는 공통 부분을 명확히 분리한다.
2. 사용자(코치)가 플레이 도중 아무 때나 채팅으로 끼어들 수 있는 채널을 시스템 차원에 내장한다.
3. AI(프로게이머)가 코치 말을 그대로 실행하지도, 무시하지도 않고, 자기 상황 판단에 접목해서 반응하도록 만든다.
4. AI가 게임 규칙을 사람처럼 처음엔 힘들게 배우고, 배운 걸 스스로 압축해서, 실전에서는 리소스를 최소한으로만 쓰도록 만든다.

## 실행 환경: "로컬에서 돌린다"가 정확히 뜻하는 것
이 문서 전체에서 "로컬"이라고 부르는 건 게임 자체와, 그 게임을 조작하는 손발(캡처·전술 계층·입력 실행·녹화·대시보드)이 전부 하나의 컴퓨터(하나의 OS) 위에서, 사람이 직접 플레이할 때와 완전히 같은 방식으로 돌아간다는 뜻이다. 이 컴퓨터의 실제 마우스 커서와 키보드 포커스를 에이전트가 그대로 가져가서 쓴다 — 어딘가 가상의 게임 서버나 클라우드 게임 스트리밍 서비스를 쓰는 게 아니다.

### 이 한 대의 컴퓨터 위에서 도는 것 (전부 로컬, 네트워크 왕복 없음)
- **Chrome/Chromium 브라우저 창** — Playwright는 이 창의 위치·크기만 고정할 뿐, 브라우저 자체는 이 컴퓨터에서 실제로 실행된다. 그 안에서 flasharch.com의 Ruffle 에뮬레이터가 고군분투를 실제로 구동
- **mss**가 이 브라우저 창을 스크린샷으로 캡처
- **OpenCV(전술 계층)**가 그 스크린샷에서 캐릭터·발판 위치를 분석
- **pynput**이 이 컴퓨터의 실제 OS 입력 큐에 클릭 이벤트를 흘려보냄 — 시스템 입장에선 사람이 마우스를 클릭한 것과 구분되지 않음
- **OBS**가 이 화면을 녹화
- **FastAPI + SQLite 대시보드 서버**도 이 컴퓨터에서 함께 실행

### 유일하게 "로컬이 아닌"(원격 API 호출) 부분
- **전략 계층의 LLM 판단** — Claude API로 인터넷을 통해 요청을 보내고 응답을 받음 (부록 1에서 계산한 1~3초 지연의 원인이 바로 이 왕복)
- **코치 음성 파이프라인의 STT/TTS** — Deepgram·ElevenLabs도 클라우드 API 호출

정리하면: 게임과 그걸 조작하는 "몸"은 전부 한 컴퓨터 안에 있고, "뇌"(LLM 판단)와 "귀·입"(음성 인식/합성)만 인터넷 너머로 오간다.

### 실무적으로 중요한 함의
이 컴퓨터의 실제 마우스·키보드를 에이전트가 점유하기 때문에, 플레이 중엔 그 컴퓨터로 다른 작업을 동시에 하기 어렵다. 방법은 두 가지다.
1. **이 프로젝트 전용 컴퓨터(또는 미니PC)를 한 대 따로 둔다** — 가장 단순하고, 처음 시작할 땐 이쪽을 권한다.
2. **가상 디스플레이 + 가상 입력장치로 화면에 안 보이게 돌린다**(리눅스라면 Xvfb 등) — 평소 쓰는 컴퓨터를 그대로 쓸 수 있지만 설정이 더 복잡하다.

또한 "로컬"이 꼭 사용자의 개인 데스크탑이어야 하는 것도 아니다. 핵심은 "게임+캡처+입력 루프가 하나의 OS 위에 통째로 올라가 있는 것"이지, 그 OS가 물리적 PC인지 직접 빌린 클라우드 VM(가상 디스플레이 포함)인지는 상관없다 — 다만 지금 단계에서는 사용자의 실제 PC(또는 이 프로젝트 전용으로 할당한 PC 한 대)가 가장 단순한 시작점이다.

## 신규 핵심 개념: 학습 → 압축 → 목표설정 → 실행 파이프라인
기존 설계는 "전술 계층은 게임마다 사람이 새로 코딩한다"는 전제였다. 이번 아이디어는 그 전제를 바꾼다 — 사람이 미리 규칙을 정해주는 대신, AI가 사람처럼 게임을 먼저 겪어보며 배우고, 배운 걸 스스로 압축해서 실행 규칙을 만들게 한다. 그러면 "게임마다 새로 구현해야 한다"고 했던 부분 자체가 AI의 산출물이 된다.

이 흐름은 사람의 운동 기술 습득 과정과 정확히 대응된다. 스포츠심리학/운동학습 이론에서 널리 쓰이는 3단계 모델(인지 단계 → 연합 단계 → 자동화 단계)과 같은 구조다 — 처음엔 의식적으로 하나하나 신경 쓰며 배우고(느리고 실수 많음), 점점 패턴이 규칙으로 정리되며, 마지막엔 거의 무의식적으로 빠르게 실행하게 된다.

```
Phase L0: 관찰 학습 (1회성, 고비용)
   → Phase L1: 규칙 압축 (매뉴얼 작성)
      → Phase L2: 목표 설정
         → Phase E: 실전 실행 (저비용, 반복 — 아래 "계층별 설계"가 여기 해당)
```

### Phase L0 — 관찰 학습 (1회성, 고비용)
두 가지 소스를 상황에 따라 쓴다.
- **소스 A: 게임 내장 튜토리얼**: 게임 자체에 튜토리얼이 있으면 AI가 화면(텍스트, 화살표, 하이라이트)을 보고 지시를 따라 직접 연습하며 관찰
- **소스 B: 사람 시연 관찰**: 코치가 직접 플레이하는 동안, 화면 프레임과 실제 키보드/마우스 입력(정확한 타임스탬프 포함)을 동시에 기록. 이후 AI가 "화면이 이렇게 변하는 시점에 이런 입력이 들어갔다"는 동기화된 데이터를 짧은 클립 단위(예: 성공한 점프 1회 구간)로 분석해 패턴을 추출

이 단계는 매 순간을 깊이 분석해야 하므로 비용·시간이 크다 — "Claude Plays Pokémon"급 리소스(행동당 10초 이상, 여러 문단짜리 추론)를 기꺼이 쓸 구간이다. 다만 게임당 1회성 투자이므로, 이후 반복되는 실행 비용에 비하면 충분히 감당할 만하다.

### Phase L1 — 규칙 압축 (컴파일)
관찰한 내용을 짧은 "게임 플레이 매뉴얼"로 압축한다. 예시(고군분투):
```
게임: 고군분투
조작: 마우스 좌클릭만 사용 (키보드 불필요)
행동 규칙:
 1. 발판이 사라지는 시점 → 좌클릭 1회 (점프)
 2. 목표가 다음 발판이 아니라 벽/건물이면 → 공중에서 좌클릭 1회 더 (와이어)
예외: 매뉴얼에 없는 새로운 패턴 발견 시 → 전략 계층 재분석 요청
```
이 매뉴얼이 바로 전술 계층 로직 + 전략 계층 게임 컨텍스트의 실제 원료다. 사람이 수동으로 정하는 게 아니라, AI가 스스로 도출한 규칙을 그대로 코드/프롬프트로 옮기는 것이다.

### Phase L2 — 목표 설정
매뉴얼이 정리된 뒤에야 "이번 판의 목표"를 정한다 — 클리어 자체, 코인/점수 극대화, 특정 구간 스피드런 등. 코치가 지정하거나 AI가 제안할 수 있고, 실행 중에도 코치가 채팅으로 갱신할 수 있다.

### Phase E — 실전 실행 (저비용, 반복)
매뉴얼에 있는 규칙은 대부분 전술 계층에서 LLM 호출 없이 그대로 실행된다. 전략 계층(LLM)은 더 이상 "매 1~3초마다 계속 도는" 게 아니라, 매뉴얼에 없는 새로운 상황이 벌어졌을 때만 개입한다 — 예외 처리 + 목표 추적 + 코치 응대로 역할이 좁아진다. 이 덕분에 부록에서 계산한 1~3초 지연이 사실상 병목이 되지 않는다. 애초에 자주 호출할 필요가 없어지기 때문이다.

### 재학습이 필요한 경우
진행 중 매뉴얼에 없는 새 패턴이 나타나면(예: 고군분투 5단계의 급격한 난이도 상승), 그 구간만 Phase L0~L1을 짧게 다시 거쳐 매뉴얼을 갱신하는 걸 권한다. "매뉴얼이 스테이지를 거치며 점점 두꺼워지는 과정" 자체가 좋은 성장 스토리 콘텐츠가 된다.

## 전체 구조 개요
아래는 Phase E(실전 실행 단계)의 구조다 — Phase L에서 만들어진 매뉴얼이 이미 있다는 전제다.
```
                         ┌─────────────────────┐
                         │   코치 인터페이스      │  ← 사용자가 아무 때나 채팅 입력
                         │  (Coach Channel)     │
                         └──────────┬───────────┘
                                    │ 메시지 큐
                                    ▼
[화면 캡처] → [전술 계층: 게임별 트래커] ⇄ [실행 계층: 키보드/마우스]
                     ▲
                     │ 상황 요약
                     ▼
              [전략 계층 = "프로게이머 두뇌"]
                - 상태 메모리(현재 계획/자기 판단)
                - 코치 메시지 반영 판단
                - 코치에게 응답 생성
                     │
                     ▼
              [로깅/하이라이트 계층] → 영상 제작용 데이터 (판단 로그 + 코치-AI 대화)
```
핵심은 전술 계층만 게임마다 새로 만들고(이제는 Phase L0~L1을 통해 AI가 스스로 만들어냄), 나머지(캡처/전략 엔진/코치 채널/실행/로깅)는 그대로 재사용한다는 것이다.

## 계층별 설계

### 1. 캡처 계층 (공통, 게임 무관)
일정 주기로 게임 화면을 캡처. 게임이 바뀌어도 코드 변경 없음.

### 2. 전술 계층 — (정정) 게임마다 코드를 새로 짜지 않는, 범용 인지 스택
지금까지 예시로 든 "고군분투는 `cv2.inRange`로 색상 추적한다"는 설명은 이 게임 하나에 맞춘 특수 사례였지, 시스템의 기본 설계가 아니었다. 이대로면 게임마다 사람(또는 AI)이 매번 새로운 CV 코드를 손으로 짜야 하는데, 그건 "어떤 게임이든 배우는 글로벌 시스템"이라는 목표와 어긋난다. 아래처럼 고쳤다 — 알고리즘은 모든 게임에서 100% 동일하게 재사용하고, 게임마다 달라지는 건 그 알고리즘에 주는 "무엇을 추적할지"라는 초기화 값뿐이다.
- 공통 인터페이스는 그대로 유지: `현재 상황 감지()`, `행동 실행(의도)`
- 다만 `현재 상황 감지()`의 내부 구현이 게임별 맞춤 코드가 아니라, 범용 추적 알고리즘 + Phase L0/L1이 자동으로 만들어주는 초기화 파라미터로 바뀐다
- 게임이 바뀌어도 코드 자체는 그대로고, Phase L0/L1이 새 게임을 관찰해서 "이번엔 이 물체를 이렇게 추적하라"는 설정값만 새로 만들어낸다

### 2-A. 범용 인지 스택 — 게임마다 CV 코드를 새로 짜지 않는 3단계 구조
"게임별로 색상 임계값을 하드코딩"하는 대신, 속도가 다른 3단계 인지 도구를 계층으로 쌓고, AI가 관찰을 통해 이 도구들에게 "무엇을 찾을지"만 알려주는 구조로 설계한다. 알고리즘 코드는 게임과 무관하게 100% 동일하다.

| 단계 | 도구 | 속도 | 게임 무관 이유 |
|---|---|---|---|
| **1단계(매 프레임)** | 범용 객체 추적기(OpenCV `KCF`/`CSRT`/`MOSSE`) | GPU 불필요, CPU만으로 실시간(수십~수백 fps) | 색상·모양을 몰라도 "이 바운딩박스 안의 무언가"를 계속 따라감 — 어떤 게임 그래픽이든 동일 코드로 작동 |
| **2단계(주기적 재탐지)** | 제로샷 개방어휘 탐지기(YOLO-World 등) | GPU 있으면 실시간급(예: V100에서 약 74fps) | "플레이어 캐릭터", "발판" 같은 자연어 설명만으로 화면에서 위치를 다시 찾아냄 — 학습·미세조정 없이 어떤 게임에도 적용 |
| **3단계(예외 상황)** | 전략 계층(Claude 비전, 이미 있는 것) | 1~3초 | 이미 100% 게임 무관 — 1·2단계가 실패했을 때만 호출 |

동작 흐름: AI(전략 계층 또는 Phase L0)가 처음 한 번 "이게 캐릭터다"라고 지목(바운딩박스 또는 "플레이어 캐릭터"라는 텍스트 설명) → 1단계 추적기가 그 뒤로는 매 프레임 빠르게 따라감(같은 알고리즘, 게임 무관) → 추적을 놓치면(가려짐, 화면 전환 등) 2단계가 같은 텍스트 설명으로 화면 전체에서 다시 찾아 1단계를 재초기화 → 그래도 안 되면 3단계(LLM)가 처음부터 다시 판단.

**중요한 하드웨어 전제**: 2단계는 GPU가 있어야 실시간에 가깝다. 같은 계열 모델인 SAM2는 GPU(Apple M4 기준)에서 약 44fps지만, CPU만으로는 이미지 한 장에 20초 이상 걸린다는 실측이 있다 — 즉 GPU 없는 로컬 컴퓨터라면 2단계는 "매 프레임"이 아니라 "가끔 재탐지할 때만" 쓰는 식으로 빈도를 낮춰야 한다. Grounding DINO 같은 더 무거운 모델은 쿼리당 약 0.76초로 이 루프엔 아예 부적합해서 후보에서 제외했다 — YOLO-World가 지금 기준 "개방어휘 + 실시간급"을 동시에 만족하는 사실상 유일한 선택이다.

**고군분투 재해석**: 이전 예시의 색상 임계값 코드는 폐기하지 않아도 된다 — 다만 그건 "1단계 추적기 대신 쓸 수 있는, 이 게임에서만 통하는 지름길"로 재분류한다. 시스템의 기본 경로는 항상 위 3단계이고, 특정 게임이 유난히 단순해서 더 가벼운 방법이 통하면 Phase L1이 "이 게임은 색상 임계값만으로 충분하다"고 판단해 지름길을 쓰는 것도 허용하는 정도가 맞는 절충점이다.

### 2-B. GPU가 없을 때의 2단계 대안
2단계(YOLO-World급 실시간 GPU 추론)를 쓸 수 있는 고성능 GPU가 없는 경우, 아래 순서로 대안을 검토한다. 등급을 낮출수록 구현은 간단해지지만 범용성이나 견고함이 조금씩 줄어드는 트레이드오프다.
1. **(기본 권장) 2단계를 건너뛰고 3단계로 직행**: 어차피 2단계는 "1단계가 놓쳤을 때만" 드물게 호출되는 역할이다. GPU가 없다면 그냥 2단계 자체를 두지 않고, 1단계 추적기가 놓치면 곧바로 3단계(이미 쓰고 있는 Claude 비전)를 호출해 "지금 화면에서 캐릭터가 어디 있는지" 다시 물어보면 된다. 새 인프라가 전혀 필요 없고, 재탐지가 자주 일어나는 게 아니라면 API 비용 증가도 미미하다.
2. **CPU 전용 경량 세그멘테이션 모델**: FastSAM-s는 GPU 없이 CPU만으로 실측 약 58ms/이미지(약 17fps)가 보고돼 있다 — "완전한 실시간"은 아니지만 재탐지처럼 가끔 호출되는 용도로는 충분히 쓴다. MobileSAM은 원본 SAM보다 인코더가 약 56배 빠르고(GPU 기준 약 10ms) 파라미터 수도 109배 작아서, 저사양 GPU(예: 노트북 내장 GPU)에서도 시도해볼 만하다. 둘 다 로컬에서 완전히 무료로 돌아간다.
3. **드물게 쓰는 온디맨드 클라우드 GPU**: 2단계 호출 자체가 드물다는 점을 이용해, 평소엔 서버를 안 띄우고 필요할 때만 GPU 인스턴스가 켜지는 서버리스 GPU(RunPod, Modal 등)에 YOLO-World/SAM2를 올려두고 그때만 호출하는 방법이다. RunPod 기준 T4 GPU가 시간당 약 $0.40, 초 단위 과금이라 유휴 시간엔 비용이 없고, 콜드스타트도 FlashBoot 기술로 200ms 이하까지 나온다 — 재탐지가 세션당 몇 번 안 되는 이 프로젝트 특성상 실제 청구액은 미미할 가능성이 높다. 다만 이건 네트워크 왕복이 다시 생기는 방식이라, "완전히 로컬"이라는 원칙에서는 한 걸음 벗어난다.
4. **classical CV 재탐지(모델 없이)**: Phase L0에서 처음 캐릭터를 지목할 때 그 영역을 이미지 패치로 저장해두고, 추적을 놓치면 `cv2.matchTemplate`로 화면 전체를 다시 스캔해 같은 패치를 찾는 방법이다. 딥러닝 모델이 전혀 없어 GPU/CPU 부담이 가장 적지만, 캐릭터 모양이 애니메이션 중 크게 바뀌는 게임에서는 매칭이 잘 안 될 수 있다.

이 프로젝트 규모(1인, 가끔 재탐지)에는 1번(그냥 3단계로 직행)이 가장 무난한 시작점이고, 나중에 재탐지가 너무 잦아 API 비용/지연이 부담되면 2번(FastSAM CPU)이나 3번(온디맨드 GPU)으로 승격하는 순서를 권한다.

### 3. 전략 계층 = "프로게이머 두뇌" (엔진은 공통, 컨텍스트만 게임별)
세 가지 구성요소로 나눈다.

#### 3-1. 상태 메모리 (Player State)
LLM 호출은 매번 "새 대화"이기 때문에, 프로게이머로서의 연속성(방금까지 뭘 하려고 했는지, 최근 성과가 어땠는지)을 잃지 않으려면 호출 사이에 유지되는 상태를 직접 관리해야 한다. 대략 이런 항목이면 충분하다.
- 현재 계획/목표 (예: "3번째 지붕까지는 안전하게, 이후 속도 우선")
- 최근 시도 결과 요약 (예: "직전 5번의 점프 중 3번 실패, 와이어 타이밍이 이르다는 판단")
- 코치와 나눈 최근 대화 맥락 (합의했던 것, 반박했던 것)

숫자로 된 "확신도 점수" 같은 걸 따로 설계할 수도 있지만, Phase 0에서는 과설계다. 위 세 가지를 자연어 텍스트로 매 판단 사이클마다 프롬프트에 실어 보내는 것만으로 LLM이 스스로 "지금은 확신이 있다/없다"를 맥락상 판단하게 하는 쪽을 권한다.

#### 3-2. 코치 입력 큐 (Coach Channel)
사용자가 언제든 텍스트를 보낼 수 있는 창구(Phase 0은 터미널 입력만으로 충분, 나중에 영상 제작을 고려하면 간단한 오버레이/웹 채팅창으로 확장 가능). 들어온 메시지는 큐에 쌓였다가, 다음 전략 판단 사이클에서 한꺼번에 프롬프트에 포함된다. 메시지 종류를 시스템이 구분할 필요는 없다 — "진지한 조언"이든 "엉뚱한 목표"든 그냥 코치의 발화로 취급하고, 반응은 전적으로 AI의 판단에 맡긴다.

#### 3-3. 판단 사이클 (프롬프트 구성)
매 전략 판단 사이클마다 LLM에게 넘기는 정보를 이렇게 구성한다.
```
[페르소나 지침 — 고정]
"당신은 자신만의 스타일과 판단 기준을 가진 프로게이머입니다.
 코치의 말은 신뢰할 만한 조언이지만, 지금 상황에서 그대로 따르는 게
 무리라고 판단되면 코치에게 이유를 설명하고 자기 방식대로 갈 수 있습니다.
 반대로 코치 말이 타당하다고 느끼면 자기 계획에 녹여서 반영하세요.
 매뉴얼에 없는 상황을 만나 확신이 서지 않으면, 무리해서 혼자 판단하기보다
 안전한 타이밍에 코치에게 먼저 물어보세요.
 매 판단마다 (1) 다음 행동 (2) 코치에게 남길 말(있다면) (3) 코치에게 묻고 싶은
 질문(있다면)을 함께 출력하세요."

[현재 상태 메모리]
[최근 게임 화면 스크린샷]
[전술 계층이 감지한 현재 상황 요약 — 지금이 "안전 지점"인지 여부 포함]
[코치가 이번 사이클에 새로 보낸 메시지, 있다면 (텍스트 채팅 또는 음성 인식 결과)]
```
LLM 출력은 세 갈래로 쓴다: ① 전술 계층에 넘길 다음 행동 의도, ② (있다면) 코치에게 보내는 응답 텍스트, ③ (있다면) 코치에게 먼저 던지는 질문 — 이게 자막 오버레이 + 음성(TTS)으로 함께 나가면 그대로 영상 콘텐츠가 된다.

#### 3-4. 코치 의견 수용 방식
설계 원칙은 하나다 — "명령이 아니라 참고 정보로 흘려보낸다." 시스템이 강제로 코치 말을 우선시키는 규칙을 두지 않고, 프롬프트 지침과 상태 메모리(최근 성과)를 통해 LLM이 자연스럽게 "잘 되고 있으면 자기 방식 고수, 안 되고 있으면 코치 제안에 더 열려있음" 같은 태도를 스스로 형성하게 둔다. 이게 실제 프로게이머-코치 관계와 가장 비슷한 그림이다.

### 4. 실행 계층 (공통)
OS 레벨 키보드/마우스 이벤트. 게임 무관, 이미 정의된 대로 재사용.

### 5. 로깅/하이라이트 계층 (공통)
판단 로그, 전술 계층 실행 로그에 더해 코치-AI 대화 로그도 함께 타임스탬프로 기록한다. 이후 편집 단계에서 "코치가 개입한 직후 AI가 어떻게 반응했는지"를 하나의 콘텐츠 단위로 바로 뽑아 쓸 수 있게 하기 위함이다. 이 로그는 파일이 아니라 SQLite DB에 남긴다 — 자세한 스키마와 이유는 아래 "웹 대시보드 & 데이터 계층" 절 참고.

### 6. 코치 인터페이스 (공통, 신규)
Phase 0은 최소 구현(터미널 stdin을 별도 스레드로 읽어 큐에 적재)으로 시작하고, Phase 1(녹화 단계)에서 실제 스트리밍 채팅처럼 보이는 간단한 오버레이로 확장하는 걸 권한다 — 그래야 시청자 입장에서도 "코치가 실시간으로 개입하는 방송"처럼 읽힌다.

## 코칭 채널 확장: 음성 대화 + AI의 자발적 질문
지금까지의 코치 채널은 "텍스트를 큐에 넣고, AI가 반영 여부를 판단해서 텍스트로 답한다"는 편도 중심 구조였다. 이번엔 여기에 두 가지를 더한다 — 음성으로 실제 대화하듯 주고받기, 그리고 AI가 궁금할 때 먼저 묻기.

### 1) 코치 → AI: 음성 입력 파이프라인
```
코치 음성 → VAD(발화 구간 감지) → STT(스트리밍 전사) → 확정 텍스트
   → 기존 "코치 입력 큐"에 그대로 합류 (텍스트 채팅과 동일하게 취급)
```
- **VAD(발화 감지)**: Silero VAD — CPU 단일 스레드에서 30ms 청크 하나를 1ms 미만에 처리한다고 공식 보고돼 있어, 이 파이프라인에서 사실상 지연을 신경 쓸 필요가 없는 구간이다.
- **STT(음성→텍스트)**: 실시간 스트리밍 STT API(예: Deepgram) — 공식 문서 기준 전사 지연 300ms 이하를 목표로 설계돼 있고, 종료 감지(발화가 끝났다고 판단하는 시점)까지 포함해 실측 200~500ms대다.
- 스트리밍 중 중간(interim) 텍스트는 화면 표시용으로만 쓰고, 판단에는 확정된 최종 텍스트만 반영한다 — 말이 끝나기 전 어중간한 텍스트로 AI가 오판하는 걸 막기 위함이다.
- 텍스트든 음성이든 큐에 들어가는 순간부터는 기존 설계(3-2)를 그대로 재사용 — 시스템이 입력 종류를 구분할 필요가 없다는 원칙은 그대로 유지된다.

### 2) AI → 코치: 음성 출력 파이프라인
전략 계층 출력의 "코치에게 남길 말"을 TTS로 실제 음성 합성해서 재생한다.
- **TTS(텍스트→음성)**: ElevenLabs Flash(스트리밍) — 공식 문서 기준 모델 추론 자체는 약 75ms, 동북아시아 기준 첫 오디오 바이트까지(TTFB) 150~200ms — 실제 대화처럼 느껴지는 반응속도다.
- 자막 오버레이와 음성 재생을 동시에 내보내면, 무음으로 시청하는 사람도 내용을 놓치지 않는다.

### 3) 왕복 지연시간 현실적 추정
코치가 말을 마친 순간부터 AI의 음성 응답이 시작되기까지:

| 구간 | 예상 시간 |
|---|---|
| VAD+STT 확정 | 약 0.3~1초 |
| LLM 판단 (부록 1 기준) | 약 1~3초 |
| TTS 첫 오디오 | 약 0.2~0.3초 |
| **합계** | **약 2~4초** |

사람 사이의 무선 통역 지연 정도의 체감으로, "대화하듯" 느껴지는 데 무리가 없는 범위다. 다만 고군분투처럼 프레임 단위 타이밍이 필요한 구간에서는 이 2~4초 동안 게임이 계속 진행되므로, 아래 "자발적 질문" 설계에서처럼 안전 지점에서만 음성 대화를 트리거하는 게 중요하다.

### 4) AI의 자발적 질문 — 언제, 어떻게
기존에는 전략 계층이 "예외 상황을 만나면 스스로 판단"하는 것까지만 설계했는데, 여기에 "판단이 안 서면 코치에게 먼저 묻는다"는 선택지를 추가한다.
- **Phase L0(학습) 중**: 튜토리얼/시연을 관찰하다 애매한 지점을 만나면 자유롭게 질문 가능 — 이 단계는 실시간 압박이 없어서, 필요하면 재생을 멈추고 다시 보여달라고 요청할 수도 있다.
- **Phase E(실행) 중**: 매뉴얼에 없는 예외 상황을 만났을 때 — 하지만 게임이 실시간으로 흐르므로 아무 때나 물을 수는 없다. 전술 계층이 판단한 "안전 지점"(예: 고군분투라면 착지 직후, 다음 장애물 구간 시작 전처럼 입력이 급하지 않은 순간)에서만 질문을 던지고, 코치의 답이 늦으면 최선의 판단으로 우선 진행한 뒤 결과를 나중에 보고한다.

### 5) 질문-답변이 매뉴얼 갱신으로 이어지는 구조
질문에 대한 코치의 답은 그 판단 한 번으로 끝나지 않는다. 그 즉시 상태 메모리에 "새로 배운 규칙"으로 기록되고, 다음에 같은 상황이 오면 매뉴얼을 참고해 질문 없이 바로 실행한다.
```
플레이 중 예외 상황 발생
   → (안전 지점에서) AI가 질문 → 코치가 음성/채팅으로 답변
   → 상태 메모리에 "학습된 규칙"으로 즉시 반영
   → 같은 상황 재발생 시: 더 이상 안 묻고 매뉴얼대로 실행
```
이게 바로 "수업이 끝난 뒤 몰아서 질문하는 게 아니라, 필요한 순간에 물어서 감각과 이해를 그때그때 연결시키는" 구조의 실제 구현이다. "재학습이 필요한 경우"에서 언급했던 매뉴얼 갱신이 사실 이 메커니즘 — 자발적 질문이 재학습을 촉발하는 실제 방아쇠다.

### 6) 주의: 질문 빈도는 억제해야 합니다
사람도 매 순간 질문하면 배우는 속도가 오히려 느려지고 대화 상대도 지친다. 콘텐츠 관점에서도 AI가 너무 자주 끼어들면 게임 진행의 몰입감과 템포가 깨진다. 억제 장치를 세 가지 권한다.
1. 확신이 정말 낮을 때만 질문하도록 페르소나 프롬프트에 명시 (숫자 점수화는 여전히 과설계 — LLM의 자체 판단에 맡긴다)
2. 같은 종류의 질문은 세션당 반복하지 않도록 상태 메모리에 "이미 물어본 것" 기록
3. Phase E 중에는 반드시 "안전 지점"에서만 질문 — 언제든 끼어드는 게 아니라 게임이 허락하는 순간에만

## 웹 대시보드 & 데이터 계층
지금까지 "코치 인터페이스"는 실시간 채팅/음성 창구로만 다뤘는데, 여기에 모든 조작(제어)과 조회(로그·통계)를 웹 페이지 하나에서 처리하는 대시보드로 범위를 넓힌다. 원칙은 두 가지다 — ① 처음부터 무거운 DBMS/프론트엔드 프레임워크를 쓰지 않는다, ② 필요해지면 갈아끼울 수 있는 형태로 시작한다.

### 1) DB: SQLite로 시작 (근거 기반 판단)
이 프로젝트는 사실상 에이전트 프로세스 하나가 유일한 writer이고(코치가 조작하는 것도 결국 같은 서버를 거쳐 한 곳에 기록됨), 대시보드에서 여러 사람이 본다 해도 그건 대부분 읽기다. SQLite는 정확히 이런 워크로드에 강하다.

| 지표 | SQLite 실측 벤치마크 |
|---|---|
| 쓰기 처리량 | 초당 약 10,000~50,000 트랜잭션 (단, 동시 writer는 1개) |
| 동시 writer | 약 10~20개까지는 무리 없음, 그 이상은 잠금 경합 증가 |
| 읽기 처리량 | 초당 100,000+ 쿼리, 서브밀리초 응답(네트워크 왕복 없음) |

**PostgreSQL 등 DBMS로 전환해야 할 신호**(이 중 하나라도 실제로 발생하면 그때 이전):
- 초당 수천 건의 동시 쓰기가 필요해짐 (예: 여러 에이전트 인스턴스를 동시에 돌리는 시나리오)
- 앱 서버를 여러 대로 늘려야 함
- 데이터가 1TB를 넘어갈 정도로 커짐
- 내장 복제/이중화가 필요해짐

1인 프로젝트에서 게임 하나 플레이하며 로그를 쌓는 지금 규모는 이 신호들과 거리가 멀어서, SQLite로 시작하는 게 "가볍게 시작"이라는 원칙에 맞을 뿐 아니라 성능상으로도 근거가 있는 선택이다. `PRAGMA journal_mode=WAL`(Write-Ahead Logging)만 켜두면 읽기(대시보드 조회)와 쓰기(로그 기록)가 서로 거의 안 막는다.

### 2) DB 접근: SQLModel (+ Alembic)
FastAPI 공식 문서가 직접 권장하는 조합이다 — FastAPI를 만든 사람이 만든 라이브러리로, SQLAlchemy(DB 엔진) + Pydantic(API 스키마)을 하나로 합쳐서 같은 클래스가 API 응답 스키마이자 DB 테이블 정의가 되게 해준다. 이중 관리가 없어서 소형 프로젝트에 특히 유리하다.

가장 중요한 실익은 SQLite → PostgreSQL 전환이 연결 문자열 한 줄 교체 수준이라는 점이다(SQLAlchemy가 두 DB를 동일 API로 추상화). 나중에 정말 커지면 Alembic으로 마이그레이션 스크립트를 돌려 그대로 옮기면 된다 — 지금 설계를 갈아엎을 필요가 없다.

### 3) 최소 테이블 설계
```
sessions        — 세션 단위(게임, Phase, 시작/종료 시각, 목표, 결과)
decisions       — 전략 계층 판단 로그(타임스탬프, 판단 내용, 걸린 시간, 사용 모델)
tactical_events — 전술 계층 실행 로그(타임스탬프, 액션 종류, 좌표, 성공/실패)
coach_messages  — 코치-AI 대화(텍스트/음성 통합, 발신자, 내용, 세션 참조)
questions       — AI의 자발적 질문 로그(질문, 답변, 매뉴얼 반영 여부)
manuals         — 게임별 매뉴얼(버전, 내용, 생성 출처 L0/L1, 갱신 이력)
highlight_clips — 자동 감지된 하이라이트(트리거 사유, OBS 클립 경로, 세션 참조)
```
전부 SQLModel 클래스 하나씩으로 정의하면 DB 테이블 + API 응답 스키마가 동시에 해결된다.

### 4) 백엔드: 기존 FastAPI 서버를 그대로 확장
새 서버를 따로 만들 필요가 없다 — 코치 인터페이스용으로 이미 정한 FastAPI+WebSocket 서버 하나에, REST 엔드포인트(로그 조회, 세션 목록, 매뉴얼 조회/수정)와 대시보드 페이지 서빙을 같이 얹으면 된다. "조작"(코치 메시지 보내기, 세션 시작/정지, 목표 변경, 매뉴얼 수동 승인)도 이 REST 엔드포인트로 노출하면, Phase 0-c의 터미널 입력이 자연스럽게 대시보드 안으로 흡수된다.

### 5) 프론트엔드: 빌드 파이프라인 없이 시작
React/Vue 같은 SPA 프레임워크와 빌드 도구는 지금 단계엔 과하다. FastAPI가 기본 지원하는 Jinja2 템플릿 + 약간의 순수 JS(fetch/폴링)로 로그 테이블, 세션 목록, 매뉴얼 뷰어 정도는 충분히 만들 수 있다. 실시간 갱신도 처음엔 몇 초 간격 폴링으로 시작해도 된다 — 위 표에서 보듯 SQLite 읽기는 매우 저렴해서 폴링 부하가 문제가 되지 않는다. 나중에 필요해지면 WebSocket push나 SPA 프레임워크로 갈아끼우면 되고, 그때도 백엔드(FastAPI+SQLModel)는 거의 그대로 재사용된다.

## 게임이 바뀔 때 무엇을 갈아끼우나
| 계층 | 게임이 바뀌면? |
|---|---|
| Phase L0~L1 (학습·압축 파이프라인 엔진) | 그대로 재사용 |
| 캡처 | 그대로 재사용 |
| 전술 계층 알고리즘(범용 인지 스택: 추적기+제로샷 탐지기) | 그대로 재사용 — 코드 자체는 게임 무관 |
| 전술 계층 초기화 파라미터(무엇을 추적할지) | Phase L0~L1이 관찰로 자동 생성 — 사람이 직접 코딩하지 않음 |
| 전략 계층 엔진(상태 메모리 구조, 코치 채널 연동, 판단 사이클) | 그대로 재사용 |
| 전략 계층 컨텍스트(이 게임의 규칙 설명, 목표 정의) | Phase L1 매뉴얼에서 자동 생성, 사람은 검수만 |
| 실행 계층 | 그대로 재사용 |
| 로깅/코치 인터페이스 | 그대로 재사용 |

즉 게임마다 실제로 달라지는 건 "Phase L0~L1이 만들어낸 게임 플레이 매뉴얼" 하나뿐이고, 그게 전술 계층 로직과 전략 계층 프롬프트에 함께 반영된다. 사람이 매번 새로 코딩하는 게 아니라, 파이프라인 자체는 고정해두고 매뉴얼만 게임마다 새로 생성되는 구조다.

## 고군분투 적용 예시
- 전술 계층: 범용 인지 스택 그대로 사용 — Phase L0에서 AI가 "이게 캐릭터"라고 한 번 지목하면 KCF/CSRT 추적기가 매 프레임 따라가고, 놓치면 YOLO-World(또는 색상 임계값 지름길)로 재탐지. 캐릭터·발판을 찾은 뒤의 점프/와이어 타이밍 실행 로직만 게임 고유
- 전략 계층 컨텍스트: "이 게임은 외길 타이밍 게임이며 당신이 결정하는 건 '이번이 점프인지 와이어인지'와 대략적 타이밍 여유 정도다. 정밀한 클릭 실행은 전술 계층이 담당한다"
- 코치 개입 예시: 코치가 "이번 판은 좀 무모하게 가봐"라고 치면, AI가 최근 성과 상태(예: 방금 3연속 성공 중)를 근거로 "지금 흐름이 좋아서 조금만 더 신중하게 가겠습니다"처럼 반박하거나, 반대로 반복 실패 상태라면 "알겠습니다, 이번엔 다르게 시도해보죠"처럼 수용

## 구현 순서 (학습 파이프라인 포함 최종 버전)
1. **L-a**: 관찰 학습 최소 구현 — 코치가 고군분투 1단계를 직접 플레이하는 동안 화면+입력 이벤트를 동기화해서 기록하는 로거만 먼저 구축
2. **L-b**: 기록된 시연 데이터를 AI(LLM)에게 클립 단위로 보여주고, 매뉴얼(위 예시 포맷)을 실제로 뽑아내는지 검증 — 사람이 매뉴얼 품질을 검수
3. **0-a**: 검증된 매뉴얼을 바탕으로 전술 계층(픽셀 트래킹) 구현 — 코치/전략 계층 없이 매뉴얼 규칙만으로 1단계 클리어 시도
4. **0-b**: 전략 계층 연결 — 상태 메모리 구조 확립, 매뉴얼에 없는 예외 상황에서만 개입하는지 검증
5. **0-c**: 코치 인터페이스 연결(텍스트 우선) — 터미널 입력으로 실시간 메시지 주입, AI가 상태에 맞게 반영/반박하는지 확인
6. **0-d**: 음성 채널 연결 — VAD+STT로 코치 음성을 텍스트 큐에 합류시키고, TTS로 AI 응답을 음성 출력. 이 단계에서 자발적 질문(안전 지점 판단 포함)도 함께 검증
7. **Phase 1**: 코치-AI 음성 대화를 자막/오디오로 얹어 첫 녹화

Phase 0 시작 전에 L-a/L-b를 먼저 넣은 이유는, 전술 계층을 사람이 손으로 설계하지 않고 매뉴얼 산출물을 그대로 옮기는 것이 이번에 새로 정한 원칙이기 때문이다 — 이 파이프라인이 실제로 쓸 만한 매뉴얼을 뽑아내는지부터 확인하는 게 순서상 맞다.

## 열린 질문
- 프로게이머 페르소나(말투, 성향)를 게임마다 다르게 줄지, 하나의 고정 캐릭터로 시리즈 전체를 관통시킬지
- 상태 메모리를 세션(게임 1회 플레이) 단위로만 유지할지, 여러 세션에 걸쳐 "장기 기억"(예: 이전 방송에서 배운 것)까지 이어지게 할지
- 사람 시연 데이터를 AI에게 보여줄 때 클립을 얼마나 잘게 쪼갤지(예: 성공한 점프 1회 단위 vs 스테이지 전체)
- 매뉴얼 포맷을 사람이 읽는 텍스트로만 둘지, 전술 계층이 직접 파싱할 구조화된 형식(JSON 등)으로도 같이 만들지
- "재학습"을 언제 트리거할지 — 실패가 몇 번 반복되면 매뉴얼 갱신에 들어갈지 기준을 어떻게 정할지
- STT/TTS를 클라우드 API(Deepgram/ElevenLabs)로 갈지, 비용이 부담되면 로컬 대안(faster-whisper, 오픈소스 TTS)으로 갈지 — 지연시간과 비용의 트레이드오프
- "안전 지점"을 게임마다 어떻게 자동 판별할지 — 고군분투는 착지 순간이 비교적 명확하지만, 다른 게임에서는 이 판별 로직 자체가 매뉴얼의 일부가 되어야 할 수도 있음

## 부록: LLM 응답 지연시간 조사 — 전략 계층이 실시간 게임 분석에 적절한가
전략 계층(LLM)이 "스크린샷 캡처 → 분석 → 판단"에 실제로 몇 초나 쓰는지, 그게 고군분투 같은 실시간 게임에 맞는지를 수치로 확인했다. 결론부터: LLM 단독으로는 절대 실시간 실행에 쓸 수 없고, 이미 설계한 "전략(느림)+전술(빠름)" 2계층 분리가 필수였다는 게 수치로도 확인된다.

### 1) 기본 응답 속도 (비전 입력, 일반 모드 기준)
| 모델 | Time to First Token(첫 토큰까지) | 초당 출력 토큰 |
|---|---|---|
| Claude Haiku 4.5 | 약 0.6초 | — |
| Claude Sonnet 4 | 약 0.9초 | 약 53 tokens/s |
| GPT-4.1 | 약 1.1초 | 약 125 tokens/s |
| Gemini 2.5 Flash | 약 0.45초 | 약 205 tokens/s |

짧은 구조화 출력(예: "행동: 점프, 이유: 2문장" 수준, 약 50~150 토큰)을 요청한다고 가정하면, TTFT + 생성 시간을 합쳐 대략 1~3초가 한 번의 판단에 걸리는 현실적인 범위다. 다만 이건 "표준/비추론 모드" 기준이고, 확장 사고(extended thinking)나 고난도 추론 모드를 켜면 같은 모델이 수십~100초 이상까지 늘어날 수 있어 — 이런 모드는 절대 이 루프에 쓰면 안 된다.

### 2) 실전 사례로 검증: Claude가 실제로 포켓몬을 플레이했을 때
가장 가까운 실증 사례가 있다 — Anthropic이 공개 실험으로 진행한 "Claude Plays Pokémon"에서, 3개의 배지를 얻기까지 약 35,000번의 행동에 약 140시간의 연속 연산이 들었다고 보고되었다. 단순 계산하면:
```
140시간 × 3,600초 ÷ 35,000행동 ≈ 행동당 평균 14.4초
```
이건 매 턴마다 여러 문단짜리 깊은 추론을 거치는 "신중한" 세팅이라 우리 기준보다 훨씬 느리지만, 반대로 말하면 "LLM에게 매 순간 깊이 생각하게 하면 한 판단에 10초 이상도 걸린다"는 걸 실제 대규모 사례로 확인해주는 수치다. 이 프로젝트도 포켓몬처럼 턴제/탐험형 게임에는 이 정도 속도로도 콘텐츠가 된다(실제로 몇 달간 트위치 방송이 됐으니까). 하지만 고군분투처럼 사람도 반응 시간이 100~300ms 단위로 필요한 게임에는 1~3초는 물론 이보다 훨씬 짧은 시간도 못 쓴다.

### 3) 이미지 처리 비용도 지연시간에 영향
Claude는 이미지를 28×28px 패치 단위로 토큰화한다(`⌈가로/28⌉ × ⌈세로/28⌉`). 화면 전체를 1920×1080으로 캡처해 보내면 다운스케일 후에도 약 1,560토큰이 들어가는데, 이건 텍스트 프롬프트치고는 꽤 커서 처리 시간에 영향을 준다. 게임의 실제 플레이 영역만 크롭해서 보내면(고군분투는 화면 전체가 아니라 캐릭터 주변 좁은 영역만 판단에 필요) 토큰 수를 수백 단위로 줄일 수 있어 처리 시간 단축에 실질적으로 도움이 된다.

### 4) 결론 — 고군분투 & 공통 시스템에 적용
- 전술 계층(로컬 픽셀 트래킹)은 LLM을 절대 거치면 안 된다 — 이미 그렇게 설계했고, 이 조사로 그 결정이 필수였음이 확인됐다.
- 전략 계층의 현실적 판단 주기는 1~3초로 잡는 게 합리적이다. 더 깊은 추론이 필요한 순간(예: 코치 개입 직후 복잡한 상황 판단)에는 5~15초까지 늘어날 수 있다고 가정하고 설계하는 게 안전하다.
- 고군분투 같은 프레임 단위 게임에서는 이 1~3초조차 "매 프레임"이 아니라 "국면이 바뀔 때"(예: 다음 장애물 구간 진입 시)에만 호출하고, 그 사이는 전술 계층이 알아서 실행하는 구조가 맞다.

### 5) 지연시간을 더 줄이고 싶다면 — 대안
1. **빠른 모델 사용**: 전략 계층에 Haiku급 경량 모델 사용 (Sonnet 대비 TTFT 30~40% 단축)
2. **확장 사고 모드 끄기 + 출력 길이 제한**: `max_tokens`를 짧게 제한하고 구조화된 출력(JSON 한 줄)만 요구 — 생성 시간이 가장 큰 변수이므로 효과가 큼
3. **스크린샷 크롭/다운스케일**: 플레이에 필요한 영역만 잘라 보내 이미지 토큰 수 절감
4. **프롬프트 캐싱 활용**: 매 사이클 반복되는 시스템 프롬프트(페르소나 지침, 게임 규칙)를 캐싱하면 TTFT를 최대 50~85%까지 줄일 수 있다고 보고됨 — 화면 스크린샷 자체는 매번 바뀌어 캐싱이 안 되지만, 고정된 지침 부분은 캐싱 대상
5. **비동기 파이프라이닝**: 전략 계층 응답을 기다리는 동안 전술 계층이 직전 지시로 계속 실행하도록 블로킹하지 않는 구조 (이미 2계층 설계에 내재)
6. **로컬 경량 비전 모델(3계층 확장 옵션)**: 반응속도가 더 빠른 장르에서 API 왕복 자체가 병목이면, 네트워크 호출 없이 로컬에서 도는 소형 비전 모델(예: Moondream, Florence-2급 경량 모델)을 전략-전술 사이의 "중간 계층"으로 추가하는 것도 향후 게임 선택에 따라 고려할 만하다.

### 출처 신뢰도 참고
TTFT/처리량 표는 여러 벤치마크 집계 블로그(kunalganglani.com, dev.to 등)를 종합한 것으로, 공식 수치가 아니라 자릿수 단위의 방향성 참고치로 취급해야 한다. 반대로 Claude Plays Pokémon 사례와 이미지 토큰 계산 공식, 프롬프트 캐싱 효과는 Anthropic 공식 자료/보도 기반이라 상대적으로 신뢰도가 높다. 실제 구현 단계에서는 이 프로젝트의 실제 프롬프트·이미지 크기로 직접 측정해서 이 표를 갱신하는 게 맞다.

## 부록 2: 실제 구축 기술 스택 (근거 기반)
"이걸 써야 할 것 같다"는 추측이 아니라, 실제로 이 정확한 문제(LLM+화면+에뮬레이터/게임 자동화)를 이미 풀어본 공개 프로젝트, 벤치마크 수치, 공식 문서를 기준으로 골랐다. 특히 Claude Plays Pokémon의 실제 스타터 코드(Anthropic 관계자 David Hershey가 만든 [ClaudePlaysPokemonStarter](https://github.com/davidhershey/ClaudePlaysPokemonStarter))와, 같은 패턴을 응용한 [ClaudePlayer](https://github.com/jmurth1234/ClaudePlayer)(Claude + PyBoy 에뮬레이터 연동)가 이 프로젝트와 구조적으로 거의 동일한 선례라 가장 비중 있게 참고했다. 요약표는 [[AI 게임플레이 기술 알고리즘 정리]]에도 정리돼 있다.

### 언어/런타임
Python 3.10+. 위 두 실제 사례 모두 100% Python으로 구현돼 있고, 아래 모든 라이브러리(화면 캡처·입력 제어·CV·LLM SDK)가 Python 생태계에서 가장 성숙하다.

### 1) 화면 캡처
| 후보 | 실측 속도 | 채택 근거 |
|---|---|---|
| **mss** (기본 추천) | 1080p 기준 30~60 FPS | 크로스플랫폼, 활발히 유지보수 중, 간단한 API |
| DXcam | 1080p 기준 240+ FPS | mss보다 4~8배 빠르지만 Windows 전용, 2023년 이후 업데이트 중단 |

### 2) 입력 제어 (키보드/마우스)
| 후보 | 근거 |
|---|---|
| **pynput** (기본 추천) | 크로스플랫폼, 이벤트 기반이라 코치 인터페이스 등 다른 스레드와 연동하기 쉬움 |
| pydirectinput | (정정) pynput도 Windows에서 이미 `SendInput()`을 쓰는 것으로 소스코드에서 확인됨 — pyautogui만 구식 `mouse_event()`/`keybd_event()`를 씀. pydirectinput은 하드웨어 스캔코드 플래그를 명시적으로 써서 일부 DirectInput 전용 게임에서 여전히 더 안정적일 수 있음 |

### 3) 전술 계층 (범용 인지 스택)
- 1단계: OpenCV `KCF`/`CSRT`/`MOSSE` — GPU 없이 CPU만으로 수십~수백 fps, 전 게임 공통 코드
- 2단계: YOLO-World(제로샷 개방어휘 탐지) — GPU 있어야 실시간급(V100 기준 약 74fps)
- 3단계: 전략 계층(Claude 비전) 재사용
- Grounding DINO(쿼리당 약 0.76초), SAM2(CPU 20초 이상/이미지)는 제외

### 4) 전략 계층 (LLM)
Anthropic Claude API (Messages API, vision + 프롬프트 캐싱) — 실제 선례 2건 모두 동일 스택.

### 5) 브라우저 게임 구동 (고군분투 전용)
Playwright로 창 위치/크기만 고정, 실제 클릭은 반드시 pynput.

### 6) Phase L0 — 사람 시연 동기화 기록
OpenAI VPT 선례(마인크래프트 7만 시간, 20Hz 동기화)를 기준점으로 채택.

### 7) 녹화 및 하이라이트 클립 자동화
OBS Studio + obs-websocket v5 + `obsws-python`. Replay Buffer를 프로그래밍적으로 트리거.

### 8) 코치 인터페이스 (텍스트+음성)
FastAPI + WebSocket + HTML 오버레이. VAD: Silero VAD, STT: Deepgram 스트리밍, TTS: ElevenLabs Flash.

### 9) 로깅/상태 저장
SQLite(WAL 모드) — 자세한 내용은 위 "웹 대시보드 & 데이터 계층" 절 참고.
