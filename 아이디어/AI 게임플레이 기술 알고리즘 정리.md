# AI 게임플레이 기술 알고리즘 정리 (스냅샷)
[[AI 게임플레이 시스템 아키텍처]]에 흩어져 있는 결정사항을 한눈에 보기 위한 요약표. 상세 근거/조사 과정은 원본 문서를 참고.

## 기술 스택 (계층별)
| 계층 | 채택 기술 | 선정 근거 (요약) |
|---|---|---|
| 언어/런타임 | Python 3.10+ | 실제 선례(ClaudePlaysPokemonStarter, ClaudePlayer) 전부 Python, 아래 라이브러리 생태계가 가장 성숙 |
| 화면 캡처 | mss | 실측 1080p 30~60FPS, 크로스플랫폼, 유지보수 활발 (대안: DXcam — 240+FPS지만 Windows 전용·2023년 이후 미유지보수) |
| 입력 제어 | pynput | 크로스플랫폼, 브라우저 게임엔 충분 (네이티브 DirectX 게임 확장 시 → pydirectinput으로 교체) |
| 전술 계층 CV — 1단계(매 프레임) | OpenCV `KCF`/`CSRT`/`MOSSE` 추적기 | (정정) GPU 불필요, 바운딩박스만 주면 색상·모양 무관하게 추적 — 코드가 모든 게임에서 동일, 게임별 하드코딩 아님 |
| 전술 계층 CV — 2단계(재탐지) | GPU 있으면 YOLO-World, **GPU 없으면 생략하고 3단계(Claude 비전)로 직행이 기본 권장** | 재탐지는 드물게만 호출되므로 새 인프라 없이 3단계가 대신해도 무방. 대안: FastSAM-s(CPU 실측 약 17fps, 완전 무료) / 온디맨드 서버리스 GPU(RunPod 등, T4 시간당 ~$0.4, 콜드스타트 200ms 이하, 초 단위 과금이라 드문 호출엔 사실상 저렴) |
| 전략 계층 (LLM) | Anthropic Claude API (Messages, vision + 프롬프트 캐싱) | 실제 선례 2건이 동일 스택. 평소엔 Haiku급(빠름), 코치 개입 등 깊은 판단 필요 시 Sonnet급으로 전환 |
| 브라우저 구동(고군분투) | Playwright (창 위치 고정 용도로만, 클릭은 반드시 pynput) | 캡처 영역 안정화. Playwright 자체 클릭 API 사용 시 "OS 입력만 사용" 원칙 위반 |
| Phase L0 시연 기록 | pynput 이벤트 로거 + ffmpeg/OBS, 20Hz 동기화 | OpenAI VPT(마인크래프트 7만 시간 데이터셋)가 채택한 동기화 주기를 기준점으로 사용 |
| 녹화/하이라이트 자동화 | OBS Studio + obs-websocket v5(공식 내장) + `obsws-python` | Replay Buffer를 프로그래밍적으로 트리거해 실패 하이라이트 클립 자동 저장 |
| 코치 인터페이스(텍스트) + 웹 대시보드 | FastAPI + WebSocket, 서버 하나로 통합 | 스트리머 채팅 오버레이 표준 패턴 + 조작/조회 겸용, 새 서버 안 만듦 |
| 발화 감지(VAD) | Silero VAD | 공식 벤치마크: 30ms 청크를 CPU 단일 스레드에서 1ms 미만 처리 |
| 음성 인식(STT) | Deepgram 스트리밍 | 공식 목표 전사 지연 300ms 이하, 실측 200~500ms |
| 음성 합성(TTS) | ElevenLabs Flash(스트리밍) | 공식 문서: 모델 추론 ~75ms, 동북아 기준 TTFB 150~200ms |
| DB | SQLite (WAL 모드) | 실측 쓰기 1만~5만 tx/s·읽기 10만+ qps — 단일 writer 구조인 이 프로젝트엔 충분 |
| DB 접근(ORM) | SQLModel + Alembic | FastAPI 공식 권장, SQLite→Postgres 전환이 연결 문자열 교체 수준 |
| 대시보드 프론트엔드 | Jinja2 템플릿 + 순수 JS(폴링) | 빌드 파이프라인 없이 시작, 필요시 SPA/WebSocket push로 교체 |

비용이 부담되면 STT/TTS만 로컬 대안(faster-whisper, 오픈소스 TTS)으로 교체 가능 — 지연은 늘지만 API 비용 제거.

## 핵심 알고리즘 / 설계 개념

### 전략-전술 2계층 분리 + 범용 인지 3단계 (정정판)
- **전술 계층(빠름, 로컬)**: 화면 픽셀만 보고 밀리초 단위로 정확한 입력 실행. LLM 미개입.
- **전략 계층(느림, LLM)**: 1~3초 주기(또는 예외 발생 시점)로 고수준 판단만 수행.
- 근거: LLM 단독 latency(TTFT 0.6~1s + 생성시간)로는 프레임 단위 게임 실행 불가능 — 실측/사례 기반으로 확인됨.
- **(정정) 전술 계층은 게임별 CV 코드가 아니라 범용 인지 스택**: 1단계 범용 추적기(KCF/CSRT/MOSSE, 게임 무관 코드) → 놓치면 2단계 제로샷 개방어휘 탐지(YOLO-World, 텍스트 설명만으로 재탐지) → 그래도 안 되면 3단계 전략 계층(LLM) 호출. 게임마다 바뀌는 건 "무엇을 추적할지"라는 초기화 값뿐, 알고리즘 코드는 전 게임 공통
- **GPU 없을 때**: 2단계를 아예 생략하고 1단계가 놓치면 곧바로 3단계(Claude 비전)로 직행하는 게 기본 권장 — 재탐지는 드물게만 일어나므로 새 인프라 불필요. 완전 로컬을 유지하면서 조금 더 견고하게 하고 싶으면 FastSAM-s(CPU 실측 약 17fps), 비용을 조금 감수하고 성능을 올리고 싶으면 온디맨드 서버리스 GPU(RunPod 등, 초 단위 과금)

### 학습 → 압축 → 목표설정 → 실행 파이프라인 (Phase L0/L1/L2/E)
```
L0 관찰학습(고비용, 1회성) → L1 규칙압축(매뉴얼 생성) → L2 목표설정 → E 실전실행(저비용)
```
- L0: 게임 내장 튜토리얼 관찰 또는 사람 시연(화면+입력 동기화 기록) 분석
- L1: 관찰 내용을 조작 매핑 + 트리거조건→행동 규칙의 짧은 매뉴얼로 압축
- L2: 매뉴얼 완성 후 이번 판의 목표(클리어/점수 등) 결정
- E: 매뉴얼 규칙은 전술 계층이 LLM 없이 실행, 전략 계층은 매뉴얼에 없는 예외 상황에서만 개입
- 이론적 근거: 사람의 운동학습 3단계 모델(인지→연합→자동화 단계)과 동형 구조

### 코치 의견 수용 알고리즘
- 원칙: "명령이 아니라 참고 정보로 흘려보낸다"
- 강제 우선순위 규칙 없음 — 프롬프트 지침 + 상태 메모리(최근 성과)만 제공하고, LLM이 스스로 수용/반박 태도를 형성
- 상태 메모리 3요소: 현재 계획, 최근 시도 결과 요약, 코치와의 최근 대화 맥락 (숫자 확신도 점수는 의도적으로 배제 — 과설계 판단)

### 자발적 질문 트리거 & 실시간 매뉴얼 갱신
- 전략 계층 출력 3갈래: ① 다음 행동 ② 코치 응답(있다면) ③ 코치에게 묻는 질문(있다면)
- 질문 시점: Phase L0은 언제든, Phase E는 "안전 지점"(예: 고군분투의 착지 직후)에서만
- 질문 → 코치 답변 → 즉시 상태 메모리에 "학습된 규칙"으로 반영 → 동일 상황 재발 시 재질문 없이 매뉴얼대로 실행
- 억제 장치: 같은 질문 세션당 반복 금지, 확신 낮을 때만 질문(자연어 판단, 수치화 안 함), 안전 지점 제한

### 재학습(매뉴얼 갱신) 트리거
- 매뉴얼에 없는 새 패턴 조우(예: 고군분투 5단계 급상승) → 해당 구간만 L0~L1을 짧게 재수행
- "자발적 질문"이 재학습을 촉발하는 실제 방아쇠 역할

### 지연시간 최소화 기법 (전략 계층 호출 시)
1. 빠른 모델(Haiku급) 우선 사용
2. 확장 사고(extended thinking) 평소엔 끄고, 필요할 때만 토글
3. 스크린샷 크롭/다운스케일로 이미지 토큰 절감
4. 프롬프트 캐싱(반복되는 페르소나/규칙 프롬프트) — TTFT 최대 50~85% 절감 보고
5. 비동기 파이프라이닝 — 전략 계층 응답 대기 중에도 전술 계층은 블로킹되지 않음
6. (확장 옵션) 로컬 경량 비전 모델을 전략-전술 중간 계층으로 추가

### 하이라이트 자동 감지
- 전술/전략 계층 로그에서 "실패 패턴"(반복 실패, 이상 행동) 감지 이벤트 발생
- 이벤트 발생 시 OBS Replay Buffer를 프로그래밍적으로 트리거해 직전 N초 자동 클립 저장

### 데이터 계층 & 웹 대시보드
- **DB**: SQLite(WAL 모드)로 시작. 에이전트 프로세스 하나가 유일한 writer, 대시보드 조회는 대부분 읽기라 SQLite의 강점 구간과 정확히 일치
- **전환 신호**(발생 시에만 Postgres로): 초당 수천 건 동시 쓰기 필요 / 앱 서버 다중화 / 데이터 1TB 초과 / 복제·이중화 필요
- **ORM**: SQLModel + Alembic — FastAPI 공식 권장, SQLite→Postgres 전환이 연결 문자열 교체 수준
- **테이블(최소)**: sessions / decisions / tactical_events / coach_messages / questions / manuals / highlight_clips
- **서버**: 코치 인터페이스용 FastAPI+WebSocket을 그대로 확장 — REST(조회/조작) + 대시보드 페이지 서빙을 같은 프로세스에 통합, 새 서버 안 만듦
- **프론트엔드**: Jinja2 템플릿 + 폴링으로 시작, 필요시 WebSocket push/SPA로 교체

## 지연시간 예산 (숫자 스냅샷)
| 구간 | 예상 시간 |
|---|---|
| 전술 계층 반응(로컬, LLM 미개입) | 수 ms~수십 ms |
| 전략 계층 판단 1회 (표준 모드) | 약 1~3초 |
| 전략 계층 판단 1회 (복잡한 예외/코치 개입) | 약 5~15초 |
| 코치 음성 발화 → 텍스트 확정(VAD+STT) | 약 0.3~1초 |
| AI 텍스트 응답 → 음성 재생 시작(TTS) | 약 0.2~0.3초 |
| 코치 음성 발화 종료 → AI 음성 응답 시작 (전체 왕복) | 약 2~4초 |

## 아직 정해지지 않은 것 (열린 질문 요약)
- 프로게이머 페르소나를 게임마다 다르게 줄지 여부
- 상태 메모리의 세션 간 장기 기억 유지 여부
- 시연 데이터 클립 분할 단위
- 매뉴얼의 구조화 형식(텍스트만 vs JSON 병행)
- 재학습 트리거의 정량 기준(실패 몇 회부터)
- STT/TTS 클라우드 vs 로컬 전환 시점
- 게임별 "안전 지점" 자동 판별 로직
